# Source-policy acceptance corpus

These are **explicit expectations**, not output generated by the Rust implementation
under test. The 26 source-policy fixtures comprise 12 allowed cases and 14 rejected
cases. They freeze the decisions of the retired independent Python oracle, then
record two deliberately stronger Rust checks:

- `strict-ci-blocked-generated-marker`: after rejecting a claimed generated
  boundary without provenance, Rust also flags the handwritten `#[allow]`.
- `strict-ci-blocked-generated-root`: a Cargo target root cannot be exempted
  as generated, and its handwritten `#[allow]` is also rejected.

The `source_policy_golden.rs` Rust test invokes the **actual bundled WASI
module** via `policy-wasm/check.mjs`, not its internal Rust functions. It
compares every fixture's exit code, successful report counts and complete
ordered violation messages. An inventory mismatch fails if fixtures are added
or removed without reviewed expectations. Paths are normalized across Unix and
Windows; the compiler pin is checked against the snapshot.

Update the fixture expectations only when the intended policy semantics
change. Review the resulting diff and explain each behavioral change.
The Linux rebuild is independently checked for byte identity with the
bundled module by `policy-wasm/package.mjs verify`.

## Source-token reference corpus

`source-tokens.json` holds 213 independently computed acceptance cases: 200
historically captured mixed-token inputs and 13 manually chosen cases
covering nested comments, raw and byte strings, lifetimes, Unicode, malformed
tokens, and lint attributes. Each entry records its source text, byte-accurate
mask and ordered lint attributes. This was generated once using the retired
Python tokenizer; it is **not** recomputed from the production Rust scanner.

The Rust unit tests in `policy-wasm/src/token_golden.rs` check both the mask
and attribute extraction. `policy-wasm/token-golden.test.mjs` sends the same
inputs to the actual bundled WASI scanner on Linux/macOS/Windows and verifies
every result. Updating the frozen expectations requires an intentional review
of the semantic differences, not mechanically copying scanner output.
